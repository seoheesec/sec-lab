# SecureLens 발표 가이드

이 문서는 코드를 전부 외우기 위한 자료가 아니라, 발표자가 프로젝트의 핵심 구조와 동작 흐름을 설명할 수 있게 만든 요약본입니다.

## 1. 프로젝트 한 줄 소개

SecureLens는 사용자가 직접 입력한 코드, 업로드한 파일/폴더, 또는 GitHub 저장소를 대상으로 보안 취약점을 탐지하고, AI 분석과 오탐 필터링을 거쳐 최종 보안 대시보드와 리포트를 제공하는 프론트엔드 기반 보안 분석 웹 서비스입니다.

## 2. 기술 스택

- React: 화면을 컴포넌트 단위로 구성합니다.
- JavaScript: 분석 로직, 저장 로직, GitHub 연동 로직을 처리합니다.
- MUI: 다크모드 UI, 카드, 버튼, 입력창 같은 화면 요소를 구성합니다.
- Monaco Editor: 사용자가 코드를 붙여넣는 코드 에디터입니다.
- Recharts: 대시보드의 위험도 분포 차트를 그립니다.
- LocalStorage: 백엔드와 DB 없이 브라우저 안에 사용자, 분석 결과, 히스토리를 저장합니다.
- GitHub API: 공개 저장소의 파일 목록과 파일 내용을 가져옵니다.

## 3. 전체 사용자 흐름

1. 사용자는 로그인 또는 회원가입을 합니다.
2. 로그인 후 대시보드, 정적 분석, GitHub 연동, AI 분석, 오탐 검토, 리포트, 마이페이지를 사용할 수 있습니다.
3. 정적 분석은 코드에서 위험 패턴을 먼저 찾습니다.
4. AI 분석은 정적 분석 결과를 바탕으로 실제 공격 가능성과 수정 방향을 설명합니다.
5. 오탐 검토는 실제 취약점으로 보기 어려운 항목을 걸러냅니다.
6. 대시보드와 리포트는 오탐을 제외한 최종 취약점 수를 보여줍니다.
7. 마이페이지는 계정별 분석 히스토리, 통계, 고친 취약점 수를 보여줍니다.

발표할 때는 이렇게 말하면 됩니다:

> “SecureLens는 정적 분석으로 1차 후보를 찾고, AI 분석으로 공격 가능성을 해석한 뒤, 오탐 검토를 통해 실제로 조치해야 할 취약점만 대시보드와 리포트에 남기는 구조입니다.”

## 4. 주요 화면 역할

### Login / Signup

파일:
- `src/pages/Login.jsx`
- `src/pages/Signup.jsx`
- `src/services/authService.js`

역할:
- 사용자가 로그인해야만 기능 화면에 들어갈 수 있게 합니다.
- 회원가입 정보는 서버가 아니라 브라우저 LocalStorage에 저장합니다.
- 비밀번호는 그대로 저장하지 않고 PBKDF2 기반 해시로 저장합니다.
- 시연용 admin 계정은 자동 생성됩니다.

발표 포인트:

> “백엔드는 없지만, 프론트 단에서도 최소한의 인증 흐름을 구현했습니다. 비밀번호를 평문으로 저장하지 않고 해시 처리해서 저장하도록 구성했습니다.”

### Static Analysis

파일:
- `src/pages/StaticAnalysis.jsx`
- `src/services/analysisService.js`

역할:
- 사용자가 코드를 붙여넣거나 파일/폴더를 업로드합니다.
- `analysisService.js`의 규칙 목록을 이용해 취약 패턴을 찾습니다.
- 예를 들어 `eval(`, `os.system(`, `pickle.loads`, 문자열 결합 SQL 쿼리 같은 패턴을 탐지합니다.
- 탐지 결과는 LocalStorage에 저장되고, 대시보드와 마이페이지에서 다시 사용됩니다.

발표 포인트:

> “정적 분석은 코드를 실행하지 않고 문자열 패턴과 규칙 기반으로 위험한 코드를 찾는 방식입니다. 빠르고 안전하지만, 문맥을 완벽히 이해하지 못하므로 오탐 가능성이 있습니다.”

### GitHub Connect

파일:
- `src/pages/GithubConnect.jsx`
- `src/services/githubService.js`

역할:
- GitHub 저장소 URL을 입력하면 공개 저장소 정보를 가져옵니다.
- 파일 탐색기에서 파일을 열거나, 전체 저장소/폴더를 분석할 수 있습니다.
- 워크플로우는 정적 분석 → AI 분석 → 오탐 검토 → 리포트 준비 순서로 진행됩니다.
- 같은 저장소를 반복 분석할 때 GitHub API 호출을 줄이기 위해 캐시를 사용합니다.

발표 포인트:

> “GitHub Connect는 실제 공개 저장소를 가져와 분석합니다. GitHub API 제한을 줄이기 위해 한 번 가져온 저장소 정보와 파일 내용은 브라우저에 캐시합니다.”

### AI Analysis

파일:
- `src/pages/AIAnalysis.jsx`
- `src/services/aiAnalysisService.js`

역할:
- 정적 분석 결과를 AI에게 전달합니다.
- AI는 각 취약점이 실제로 악용 가능한지, 공격 경로가 무엇인지, 어떻게 고쳐야 하는지 설명합니다.
- API 키가 없거나 호출에 실패하면 fallback 결과를 생성해 앱이 멈추지 않게 합니다.

발표 포인트:

> “정적 분석은 패턴을 찾는 단계이고, AI 분석은 그 패턴이 실제 공격으로 이어질 수 있는지 설명하는 단계입니다.”

### False Positive Review

파일:
- `src/pages/FalsePositive.jsx`
- `src/services/falsePositiveService.js`

역할:
- AI 분석 결과 중 오탐 가능성이 높은 항목을 분류합니다.
- 예를 들어 위험도가 Low이거나, 테스트/샘플 파일에서 발견된 항목은 오탐으로 분류할 수 있습니다.
- 사용자가 직접 “오탐 신고”를 할 수도 있고, 신고 내역은 LocalStorage에 저장됩니다.

발표 포인트:

> “보안 도구에서 중요한 문제 중 하나가 오탐입니다. SecureLens는 단순히 많이 탐지하는 것보다, 최종적으로 조치 가능한 취약점을 남기는 데 초점을 맞췄습니다.”

### Dashboard / Report

파일:
- `src/pages/Dashboard.jsx`
- `src/pages/Report.jsx`

역할:
- 최종 취약점 수, 위험도 분포, 보안 점수, 보안 등급을 보여줍니다.
- 오탐 검토 결과가 있으면 오탐을 제외한 실제 취약점만 보여줍니다.
- 취약점 카드를 클릭하면 상세 설명, 공격 시나리오, 수정 가이드, 추천 수정 코드 diff를 볼 수 있습니다.
- Report 화면에서는 PDF 다운로드가 가능합니다.

발표 포인트:

> “대시보드는 기술자가 빠르게 위험도를 파악하는 화면이고, 리포트는 분석 결과를 공유하거나 제출하기 위한 화면입니다.”

### My Page

파일:
- `src/pages/MyPage.jsx`
- `src/services/scanHistoryService.js`

역할:
- 계정별 분석 히스토리를 보여줍니다.
- 총 검사 횟수, 누적 취약점 수, 오탐 제외 수, 고친 취약점 수를 계산합니다.
- 같은 파일을 다시 검사했을 때 이전에는 있었지만 이번에는 사라진 취약점을 “고친 취약점”으로 판단합니다.
- 검색, 위험도 필터, 날짜 필터를 제공합니다.

발표 포인트:

> “마이페이지는 단순 기록 저장이 아니라, 시간이 지나면서 보안 상태가 어떻게 개선되었는지 보여주는 화면입니다.”

## 5. 핵심 로직 설명

### 5.1 정적 분석 로직

파일: `src/services/analysisService.js`

핵심 함수:
- `runStaticAnalysis(code)`
- `analyzeCode(code, metadata)`
- `analyzeFiles(files)`

동작:
1. 코드를 줄 단위로 나눕니다.
2. 각 줄에 대해 취약점 규칙을 하나씩 검사합니다.
3. 규칙에 걸리면 취약점 객체를 생성합니다.
4. 파일명, 줄 번호, 취약점 유형, CWE, 위험도, 설명을 결과에 담습니다.

결과 예시:

```js
{
  type: "SQL Injection",
  cwe: "CWE-89",
  severity: "HIGH",
  line: 12,
  filePath: "app.py",
  description: "사용자 입력이 SQL 쿼리에 직접 들어갈 수 있습니다."
}
```

발표 설명:

> “이 프로젝트의 정적 분석기는 소스코드를 줄 단위로 읽고, 미리 정의된 취약 패턴에 매칭되는지 검사합니다. 예를 들어 Python의 `os.system`이나 `pickle.loads`, JavaScript의 `eval` 같은 위험 API를 찾습니다.”

### 5.2 AI 분석 로직

파일: `src/services/aiAnalysisService.js`

핵심 함수:
- `runAIAnalysis(code, vulnerabilities)`

동작:
1. 정적 분석 결과가 없으면 빈 배열을 반환합니다.
2. API 키가 없으면 fallback 분석 결과를 만듭니다.
3. API 키가 있으면 OpenAI API에 취약점 목록을 전달합니다.
4. AI 응답에서 JSON 배열을 추출해 화면에서 사용할 수 있는 결과로 변환합니다.
5. API 호출 실패 시에도 앱이 멈추지 않도록 fallback 결과를 반환합니다.

발표 설명:

> “AI 분석은 정적 분석 결과를 받아서 실제 공격 가능성, 공격 경로, 수정 방법을 설명합니다. 네트워크나 API 문제가 생겨도 서비스가 멈추지 않게 fallback 로직을 넣었습니다.”

### 5.3 오탐 필터링 로직

파일: `src/services/falsePositiveService.js`

핵심 함수:
- `runFalsePositiveReview(aiResults)`

동작:
1. AI 분석 결과를 하나씩 확인합니다.
2. `isExploitable` 값이 false이면 오탐으로 분류합니다.
3. 위험도가 LOW이면 오탐 가능성이 높다고 보고 제외합니다.
4. 파일 경로에 test, mock, example, sample이 들어가면 테스트 코드로 판단해 오탐 처리합니다.
5. 나머지는 REAL 취약점으로 남깁니다.

발표 설명:

> “오탐 검토는 실제 대응해야 하는 취약점만 남기기 위한 단계입니다. 특히 테스트 코드나 샘플 코드에서 발견된 위험 패턴은 실제 운영 위험과 다를 수 있어서 분리했습니다.”

### 5.4 분석 히스토리와 고친 취약점 계산

파일: `src/services/scanHistoryService.js`

핵심 함수:
- `compareAndSaveScan(newScanData)`
- `updateLatestScanFromFindings(...)`
- `buildScanStats(...)`

동작:
1. 새 검사 결과를 저장하기 전에 같은 파일명의 직전 검사 결과를 찾습니다.
2. 직전 검사에는 있었지만 새 검사에는 없는 취약점 ID를 찾습니다.
3. 사라진 항목을 “고친 취약점”으로 계산합니다.
4. 마이페이지에서는 이 값을 누적해서 보여줍니다.

발표 설명:

> “같은 파일을 다시 검사했을 때 이전 결과에서 사라진 취약점은 수정된 것으로 판단합니다. 그래서 마이페이지에서 ‘고친 취약점 수’를 보여줄 수 있습니다.”

### 5.5 계정별 LocalStorage 저장

파일: `src/services/storageService.js`

핵심 개념:
- 사용자 목록과 로그인 세션은 공통 저장소에 저장합니다.
- 분석 결과, GitHub 상태, 히스토리, 오탐 신고는 로그인 계정별 저장소에 저장합니다.

예시:

```text
secureLensScanHistory:admin
secureLensScanHistory:user1
```

발표 설명:

> “백엔드가 없기 때문에 LocalStorage를 사용했지만, 계정별 key를 분리해서 admin의 분석 기록이 다른 사용자에게 보이지 않도록 했습니다.”

## 6. 주요 데이터 흐름

### 직접 코드 분석 흐름

```text
코드 입력 또는 파일 업로드
→ runStaticAnalysis 또는 analyzeFiles
→ saveStaticResults
→ saveScanFromFindings
→ Dashboard / MyPage에 반영
```

### GitHub 전체 워크플로우

```text
GitHub URL 입력
→ 저장소 정보 가져오기
→ 파일 목록/파일 내용 가져오기
→ 정적 분석
→ AI 분석
→ 오탐 검토
→ 최종 결과 저장
→ Dashboard / Report / MyPage에서 확인
```

### 오탐 반영 흐름

```text
AI 분석 결과
→ runFalsePositiveReview
→ REAL과 FALSE_POSITIVE 분리
→ REAL만 최종 대시보드에 표시
→ falsePositiveCount는 마이페이지 통계에 반영
```

## 8. 발표 때 받을 수 있는 질문과 답변

### Q1. 백엔드가 없는데 데이터는 어디에 저장하나요?

A. 브라우저의 LocalStorage에 저장합니다. 사용자 계정, 로그인 세션, 분석 결과, 히스토리, GitHub Connect 상태를 저장합니다. 다만 실제 서비스에서는 보안과 확장성을 위해 백엔드 DB로 옮겨야 합니다.

### Q2. 정적 분석은 정확한가요?

A. 규칙 기반 정적 분석은 빠르고 안전하지만 문맥 이해가 제한적이라 오탐이 생길 수 있습니다. 그래서 AI 분석과 오탐 검토 단계를 추가했습니다.

### Q3. AI 분석은 무슨 역할인가요?

A. 정적 분석이 “위험 패턴을 찾는 단계”라면, AI 분석은 “이 패턴이 실제 공격으로 이어질 수 있는지 설명하는 단계”입니다. 공격 경로와 수정 방법을 자연어로 제공합니다.

### Q4. 오탐은 어떻게 처리하나요?

A. AI가 실제 악용 가능성이 낮다고 판단한 항목, 위험도 LOW 항목, 테스트/샘플 파일에서 발견된 항목은 오탐으로 분류합니다. 사용자가 직접 오탐 신고도 할 수 있습니다.

### Q5. GitHub API rate limit 문제는 어떻게 대응했나요?

A. 한 번 가져온 저장소 정보, 파일 목록, 파일 내용을 LocalStorage 캐시에 저장해서 같은 저장소를 반복 분석할 때 API 호출을 줄였습니다.

### Q6. 계정별 데이터 분리는 어떻게 했나요?

A. 분석 관련 LocalStorage key 뒤에 로그인한 사용자 ID를 붙여 저장합니다. 예를 들어 admin의 히스토리와 일반 사용자의 히스토리는 서로 다른 key에 저장됩니다.

### Q7. 실제 서비스로 확장하려면 무엇이 필요할까요?

A. 백엔드 서버, 데이터베이스, 안전한 인증 시스템, 서버 측 GitHub 토큰 관리, 분석 작업 큐, 더 정교한 정적 분석 엔진, 사용자 오탐 신고를 학습 데이터로 관리하는 기능이 필요합니다.

## 9. 발표 순서 추천

1. “왜 만들었는가”를 먼저 말합니다.
   - 개발자가 코드 보안 취약점을 쉽게 확인하고 수정 방향까지 볼 수 있게 하기 위해 만들었다.
2. 전체 흐름을 설명합니다.
   - 정적 분석 → AI 분석 → 오탐 검토 → 대시보드/리포트.
3. 직접 시연합니다.
   - 로그인 → GitHub Connect 또는 Static Analysis → Run Full Workflow → Dashboard → 취약점 카드 클릭.
4. 핵심 기술을 설명합니다.
   - LocalStorage, GitHub API, 정적 분석 규칙, AI 분석, 오탐 필터링.
5. 한계와 발전 방향을 말합니다.
   - 프론트엔드 기반이라 실제 서비스에는 백엔드와 DB가 필요하다.

## 10. 짧은 발표 대본 예시

> “SecureLens는 코드 보안 취약점 분석 웹 서비스입니다. 사용자가 코드를 직접 붙여넣거나 GitHub 저장소를 연결하면, 먼저 정적 분석으로 위험 패턴을 탐지합니다. 이후 AI 분석을 통해 해당 취약점이 실제로 악용 가능한지, 어떤 공격 경로가 가능한지, 어떻게 수정해야 하는지 설명합니다. 마지막으로 오탐 검토를 통해 실제 대응해야 할 취약점만 대시보드와 리포트에 보여줍니다. 백엔드 없이 프론트엔드와 LocalStorage만으로 구현했으며, 계정별 분석 기록과 마이페이지 통계도 제공합니다.”
